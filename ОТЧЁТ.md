# Отчёт по проекту healthchecks

Приложение [healthchecks](https://github.com/healthchecks/healthchecks) — мониторинг
cron-задач на Django — развёрнуто в Kubernetes (minikube) со всей обвязкой:
секреты в Vault, брокер, кэш, журнал событий, объектное хранилище,
автомасштабирование, нагрузочное тестирование, CI/CD и werf.

Ниже — что сделано по заданиям и где это лежит. Подробности каждого блока —
в README соответствующего каталога, ссылки в заголовках.

---

## Задание 1 — манифесты Kubernetes → [k8s/](k8s/README.md)

Ручные манифесты с префиксами-порядком: `Namespace`, `ConfigMap` с настройками,
`Deployment` веб-приложения (uWSGI) с init-контейнером `wait-for-db`, `Service`,
`PV`/`PVC`/`Secret`/headless `Service`/`StatefulSet` для Postgres, `ConfigMap`
с `uwsgi.ini`, `Job` миграций, `Deployment` фоновых процессов `sendalerts` и
`sendreports --loop`, `CronJob` чистки, self-signed CA cert-manager'а, `Ingress`
с TLS и `ExternalName`-сервис на внешний SMTP.

Начиная с Задания 2 эти ресурсы заменены релизом Helm-чарта; каталог оставлен
как справочник.

## Задание 2 — Helm-чарт и Vault → [.helm/](.helm/README.md), [deploy/vault/](deploy/vault/README.md)

Манифесты завёрнуты в чарт с `values.yaml`; Postgres, Celery-воркер и Flower
вынесены в локальные subchart'ы (`.helm/charts/*`). Subchart'ы не видят helper'ы
родителя, поэтому образ, параметры брокера и имена ресурсов передаются через
`global.*`.

Секреты хранятся в HashiCorp Vault (KV v2, mount `secret/`), а в git лежат
только ссылки `ref+vault://` ([.helm/secrets.yaml](.helm/secrets.yaml)), которые
при деплое разворачивает `helm-secrets` с backend'ом `vals`. Доступ — по AppRole
с отдельной policy на каждый компонент ([deploy/vault/policies/](deploy/vault/policies/)),
root-токен использует только [deploy/vault/setup.sh](deploy/vault/setup.sh).

## Задание 3 — RabbitMQ, AMQP и Celery → [deploy/rabbitmq/](deploy/rabbitmq/README.md), [hc/mq/](hc/mq/README.md)

Чарт `cloudpirates/rabbitmq` (bitnami-образы отдают 403 без подписки), учётка и
erlang cookie — из Vault. Management UI — через Ingress `rabbitmq.local`.

В приложении: producer/consumer поверх pika для задач к внешним API, затем
Celery-воркер (`celery -A hc worker -Q api-tasks`) и Flower как subchart'ы, плюс
API-роуты `/api/v3/tasks/<name>/` и `/api/v3/tasks/result/<task_id>/`.
Окружение собирается из нескольких Secret'ов — у каждого компонента свой,
`CELERY_BROKER_URL` склеивается в манифесте через `$(VAR)`, пароль нигде не дублируется.

## Задание 4 — Redis и кэширование → [deploy/redis/](deploy/redis/README.md), [charts/redis/](charts/redis/)

Собственный чарт Redis с `requirepass` из Vault и RedisInsight
(`redisinsight.local`) как UI. В приложении — `hc.lib.cache.CacheManager`
и cache-aside: завершённый `AsyncResult` неизменяем, поэтому кэшируется;
агрегирующий SQL для `/api/v3/tasks/stats/` — с TTL.

## Задание 5 — MongoDB и журнал задач → [deploy/mongodb/](deploy/mongodb/README.md)

Чарт `cloudpirates/mongodb` (StatefulSet + PVC), root и пользователь приложения
с правами только на свою БД — из Vault; mongo-express (`mongo-express.local`)
с basic auth. Жизненный цикл Celery-задач (`prerun`/`postrun`/`failure`)
пишется в MongoDB и отдаётся через `/api/v3/tasks/history/`.

## Задание 6 — MinIO и тела пингов → [deploy/minio/](deploy/minio/README.md)

Официальный чарт `minio/minio` в режиме standalone; bucket `healthchecks`,
policy с доступом только к нему и пользователь приложения создаются job'ами
чарта, ключи — из Vault. Console — `minio.local`.

Приложение штатно умеет складывать тела пингов в S3: тело длиннее 100 байт
уходит в MinIO (`Ping.object_size`), короткое остаётся в БД (`body_raw`).

## Задание 7 — ресурсы, нагрузка, HPA/VPA → [loadtest/](loadtest/README.md), [charts/locust-test/](charts/locust-test/README.md)

Замеры через `metrics-server`, нагрузка — Locust по реальным эндпоинтам
(`/api/v3/checks/`, `/ping/<uuid>`, `/api/v3/tasks/stats/`).

По дороге нашлись и исправлены три вещи: лимит CPU 500m (503 от ingress при
100 пользователях, поднят до 1000m), probes на `/` с `timeoutSeconds: 1`
(переведены на лёгкий `/api/v3/status/`), 8 uWSGI-процессов на 640Mi (OOMKilled,
оставлено 4). Предел одного пода — ~68 req/s при 200 пользователях.

HPA по CPU относительно `requests` (250m), цель 70%, 1–4 реплики, с `behavior`
против дребезга; `replicas` в Deployment при включённом HPA не задаётся. VPA
(`fairwinds-stable/vpa`, только recommender) в режиме `Off`: для web (API) —
только по памяти, чтобы не конфликтовать с HPA по CPU, для celery-worker — по
CPU и памяти. Распределённый прогон — через
[locust-k8s-operator](deploy/locust-operator/README.md) и CR `LocustTest`.

## Задание 8 — CI/CD и self-hosted runner → [deploy/ci/](deploy/ci/README.md)

`semantic-release` с preset `conventionalcommits` считает версию по коммитам в
`master` и ставит тег `vX.Y.Z`. [release.yml](.github/workflows/release.yml) —
три job'а: `release` (тег), `build` (образ в GHCR по тегу), `deploy` на
**self-hosted** runner'е (`runs-on: minikube-runners`) — `helm secrets upgrade`
с секретами из Vault по AppRole.

Runner'ы — Actions Runner Controller: контроллер в `arc-systems`, scale set
`minikube-runners` в `arc-runners`, `minRunners: 0` (под создаётся под job и
удаляется). Runner работает внутри кластера, поэтому kubeconfig ему не нужен —
права даёт [rbac.yaml](deploy/arc/rbac.yaml).

## Задание 9 — werf → [deploy/werf/](deploy/werf/README.md)

`werf converge` собирает образ из `docker/Dockerfile`, публикует в registry и
выкатывает чарт `.helm/` одной командой. Учётка registry — из Vault
(`secret/registry`, policy `registry-read`); секреты `ref+vault://` разворачивает
`vals` во временный values-файл, разрешённый в `werf-giterminism.yaml`.

На Windows werf запускается в официальном контейнере с Buildah-backend'ом и
делит сетевой namespace с узлом minikube, поэтому registry-аддон доступен как
`127.0.0.1:5000` — тот же адрес, по которому образ тянет kubelet.

## Восстановление с нуля

Кластер — расходный материал: код, образы в GHCR и релизы живут в git и на
GitHub, а всё содержимое minikube (namespace'ы, Vault с секретами, данные
Postgres/Mongo/MinIO/Redis/RabbitMQ, ARC, cert-manager) поднимается заново.

```sh
bash scripts/bootstrap.sh --recreate      # с пересозданием кластера
bash scripts/bootstrap.sh                 # на уже запущенном (идемпотентно)
bash scripts/bootstrap.sh --no-arc        # без self-hosted runner'а
```

[scripts/bootstrap.sh](scripts/bootstrap.sh) делает всё по порядку; порядок
продиктован зависимостями:

| # | Шаг | Почему здесь |
|---|---|---|
| 1 | `minikube start` + аддоны `ingress`, `ingress-dns`, `metrics-server`, `registry`, `dashboard` | `registry` нужен werf, `metrics-server` — HPA/VPA |
| 2 | cert-manager | выпускает все TLS-сертификаты |
| 3 | Vault + [setup.sh](deploy/vault/setup.sh) | без секретов не ставится ничего остальное |
| 4 | `minikube image build -t healthchecks:local` | `docker-env` на Windows с containerd не работает |
| 5 | RabbitMQ, Redis, MongoDB, MinIO | их Secret'ы монтирует чарт приложения — без них поды не стартуют |
| 6 | VPA, locust-operator | VPA — строго до приложения: чарт создаёт объект `VerticalPodAutoscaler`, нужен CRD |
| 7 | чарт приложения | он же создаёт `ClusterIssuer`, по которым выпускаются сертификаты всех остальных Ingress'ов |
| 8 | [seed-e2e.sh](scripts/seed-e2e.sh) | проект `e2e` с API-ключом для Locust и e2e-проверок |
| 9 | ARC | обновляет `VAULT_ROLE_ID`/`VAULT_SECRET_ID` в Secrets репозитория — AppRole пересоздан |

Два места, где порядок неочевиден и легко наступить:

* **Сертификат Vault ждёт приложение.** Ingress Vault'а ссылается на
  `healthchecks-ca-issuer`, а этот ClusterIssuer создаёт чарт приложения (шаг 7).
  До него `vault-tls` висит в `IssuerNotFound` — это нормально и чинится само.
  Сам Vault при этом работает: `setup.sh` ходит в под через `kubectl exec`.
* **Worker падает на чистой БД.** Job миграций — post-install хук, то есть
  стартует уже после `healthchecks-worker`, и тот успевает уйти в
  `CrashLoopBackOff` с `relation "api_check" does not exist`. После миграций
  bootstrap перекатывает Deployment, чтобы не ждать backoff.

### Vault после потери кластера

Старые `deploy/vault/.vault-keys.json` и `.env` относятся к уничтоженному Vault:
unseal key и AppRole из них не подойдут. `setup.sh` не станет переинициализировать
чужой keys-файл, поэтому bootstrap уводит оба файла в `*.old` (они в `.gitignore`)
и даёт скрипту сделать `operator init` заново — вместе с KV, policies, AppRole и
свежими секретами компонентов.

### Права администратора

`bootstrap.sh` их не требует: вместо `minikube tunnel` он поднимает
`kubectl port-forward` к Vault и передаёт адрес через `VAULT_ADDR_OVERRIDE`
(см. [scripts/lib.sh](scripts/lib.sh)). Для браузера туннель и hosts всё же нужны:

```
minikube tunnel                       # в терминале «от имени администратора»
```

```
# C:\Windows\System32\drivers\etc\hosts
127.0.0.1 healthchecks.local
127.0.0.1 flower.local
127.0.0.1 vault.local
127.0.0.1 rabbitmq.local
127.0.0.1 redisinsight.local
127.0.0.1 mongo-express.local
127.0.0.1 minio.local
127.0.0.1 locust.local
```
